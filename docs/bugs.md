## Closed

| B1 | S2 | YouTube trailers played ~15s then auto-advanced to the next one | Root cause: pre-roll ad ends fire onStateChange ENDED(0) before the real trailer plays, and every path advanced on the raw event. Added ad-aware end detection (progress fast-path + resume-confirm) in `src/lib/endDetection.js` (web), `TrailerPlayer.swift` (iOS), and `landing-page/api/embed.js` (proxy). v3.1.0. | 2026-07-07 |
| B2 | S2 | Trailers still stopped and skipped to the next one at ~13s (B1 regression class) | Root cause: the native 12s watchdog required a PLAYING event, but several pre-roll ad variants keep the content player UNSTARTED while the ad runs — no PLAYING fires, so live trailers were skipped as "unplayable" at 12s + ~1s load. Watchdog is now liveness-based (dead page 12s / silent player 20s / 75s hard cap) fed by a 1s proxy heartbeat; end detection hardened in all three mirrors (dual confirm window 5s→1.2s, pinned-duration fast-path gate, epoch token against stale cross-load messages); web backstop timer no longer poisonable by ad durations (+45s ad headroom). Fixed the pre-existing WKUserContentController handler retain leak while in there. v3.2.0. **Superseded by B3 — this fix was correct but incomplete and unreachable.** | 2026-07-13 |
| B3 | S2 | Trailers STILL skipped a few seconds in (B2 not actually cured) | Root cause: three variants of one mistake — trusting `onStateChange` in a bug defined by `onStateChange` not firing. (a) The only liveness signal B2 added was the `hb` heartbeat, which pre-v3.2.0 builds ignore; every installed app (2.11.0 / 3.1.0) still cancels its 12s watchdog solely on a `stateChange:1`, so redeploying the proxy fixed nothing in the field. The proxy now synthesises a `stateChange:1` (`syn:true`) once playback demonstrably advances, and owns a 75s no-playback error cap in exchange. (b) A pending end was cancellable only by a state event, so an ad pod whose next item started silently produced a false ENDED — forward playback progress now cancels it in all three mirrors (0.25s progress epsilon keeps a real end from cancelling itself). (c) The pin accepted any pre-PLAYING duration, i.e. the AD's during exactly these variants; pinning is now `initialDelivery`-only, and confirmation plus the fast-path require a pin instead of treating "no pin" as a match. Also: the native 75s hard cap now requires playback to have been frozen 20s, so it can't dismiss a playing trailer. New `embedProxy.test.js` executes the real Edge Function script (16 tests); native logic compiled and run under Linux Swift. v3.2.1. | 2026-08-14 |
| B4 | S1 | **Trailers play to the end and stop on YouTube's replay screen — they never auto-advance.** The original product-defining bug, open since v1.x through B1-B3 and five releases | Root cause, proven live 2026-08-16 against real YouTube (browser A/B on the same page/port): the proxy page only ever sent the IFrame API's `{ event:'listening' }` message — which arms the player but never asks YouTube to REPORT its state. `onStateChange`/`onError` are delivered only after an explicit `addEventListener` command. Without it the state channel is silent for the whole clip (infoDelivery keeps streaming, so every liveness/end-detection timer believed the page healthy), and the `ENDED` every mirror waits on never arrives. B1-B3 all tuned consumers of that absent event. Fix: the proxy subscribes (`addEventListener('onStateChange'/'onError')`) when the player announces itself ready — the onReady moment, which the live A/B proved is the earliest point the widget accepts the command; one retry at +2s if still silent. The subscription is player-level and survives trLoad. (The first v3.4.2 deploy anchored the send at iframe-load and retried at 2.5s; the widget drops commands posted before it boots, so on a slow cold load both sends could land pre-ready and be lost — corrected to the onReady anchor in the following proxy deploy.) Native playlist handoff (v3.4.0) disabled because the widget fires NO ENDED between playlist items (`-1→3→1`) so `playlistDidAdvance()` could never sync. v3.4.2. **Device status (as of 2026-09-21): STILL UNCONFIRMED, and the proxy redeploy that the hypothesis depends on has not happened.** Production `https://trailer-roulette.vercel.app/embed` was still serving the v1.9.0 page at the 3.5.0 review — no `announcePlaying`, no `subscribeToPlayerEvents`, no `youtubeEventsSeen`. No installed build can auto-advance until `landing-page/` is deployed. This is the first step of the 3.5.0 release sequence and `scripts/verify-production.mjs` is the gate that now fails the release workflow if it is skipped. | 2026-08-16 |

| B5 | S2 | The first-launch consent sheet appeared and animated away on EVERY cold launch, not just the first | Root cause: `hintOpen` was initialised `true` so `FirstRunHint` mounted on frame one, and `useDismissAnimation` mounts immediately and plays a 240ms exit when the parent flips `open`. The stored acceptance is read behind four awaits in the boot effect, so a returning user always saw the sheet before it resolved. A boolean cannot express "not read yet": `true` flashes the sheet, `false` flashes the player at someone who never agreed. Fix: tri-state `consentGate(stored)` in `lib/release.js` — `undefined` (never read) to `null`, an exact `POLICY_VERSION` match to `false`, anything else to `true`. Neither surface renders while null, so the player-wrap gate also moved from `!hintOpen` to `hintOpen === false`. Still fails closed on a throw. The boot comment claimed a failed read counted as "already seen" while the code did the opposite; corrected. **Follow-up the same day, from an adversarial review:** the read that leaves the unknown state sat LAST in the boot effect, behind three unrelated Preferences round-trips and `loadQueue()`. The unknown state renders neither surface, and `catch` does not cover a promise that never settles — so one stalled bridge call (plugin not yet registered, web view resumed from a background snapshot) left the app on a black stage permanently, a failure mode the old boolean could not have had. The read moved to the front of the effect and got a 3s timeout that rejects into the same fail-closed path. 15 tests, every one mutation-checked. v3.5.0. | 2026-09-21 |
| B6 | S3 | The swipe-down dismissal in the native player was unreachable — the gesture could not be started anywhere on screen | Root cause: two independently reasonable changes composed into a dead path. `chromeMayAutoHide()` was made to return `false`, so the glass header is permanently visible; `gestureRecognizerShouldBegin` rejected the header's whole frame, which had been correct while it auto-hid ("once hidden, its frame is just more stage"). Separately the web view was given the space from the header's bottom edge to the progress track, and player touches belong exclusively to YouTube. What remained was the 2.5pt progress track and the home-indicator inset — nothing a thumb can land on, and the home-indicator swipe fights it. Fix: reject the header's `UIControl`s (grown to the 44pt target) rather than the whole header, leaving the title and the empty glass draggable. Done, Mute and Skip unchanged. Four comments describing `.overFullScreen` while the code said `.fullScreen` corrected in the same pass. v3.5.0. **Not device-verified** — CI's simulator compile is green; the gesture itself has never been performed on hardware. | 2026-09-21 |
| B7 | S2 | Every iPad build rendered as a 520pt phone-width column with hairline borders and roughly half the screen black | Root cause: the "Desktop dev view" block in `styles/index.css` — a development affordance so `npm run dev` in a desktop browser looks like a device — was gated on `min-width: 900px` alone, and an iPad in portrait is about 1032px. Measured in Chromium at 1032px before the fix: `.app-shell` width 520, `max-width: 520px`, `border-left: 1px`. After: 1032, `none`, `0px`; desktop unchanged at 520; iPhone never affected. Fix: the query also requires `(hover: hover) and (pointer: fine)`, which no touch device reports, and the rule is scoped to `html:not([data-native])`, with the marker set in `main.jsx` for any Capacitor build — two independent gates, because the cost of it leaking again is a store screenshot that makes the iPad build look broken. It survived this long because the screenshot script reproduced it: Playwright without touch emulation reports a fine pointer, so the 13-inch drafts were captures of the dev view. The capture context now passes `hasTouch`/`isMobile`. 5 tests. **Confirmed on iPadOS**, not just in Chromium: the native simulator capture from `ios-screenshots.yml` fills the screen with no column and no hairlines. v3.5.0. | 2026-09-21 |

## Severity rubric
- **S1 (block submission)** — crash on launch, data loss, App Review flag
- **S2 (block release)** — major feature broken on a common device
- **S3 (fix in v1.1)** — minor visual or non-blocking interaction issue
- **S4 (nice to have)** — polish, copy, edge case
